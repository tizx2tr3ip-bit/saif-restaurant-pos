# ربط الكاشير والمطبخ — 16 أكتوبر 2026

## ما نُفّذ

- إصلاح تحميل pos.order: القائمة الفارغة في Odoo 20 تعني تحميل جميع الحقول. إضافة حقول السيارة إليها كانت تقصر metadata على حقول السيارة وتحذف علاقة lines، فتتعطل شاشة POS عند حساب الأسعار. نحافظ الآن على معنى القائمة الفارغة، ونضيف حقولنا فقط إذا حددت إضافة أخرى قائمة صريحة.
- إضافة مستقلة `saif_cafe_kitchen`: لوحة موظف على `/cafe/kitchen/<config_id>`، دخول مطلوب مع صلاحية مستخدم POS وشركة مسموحة، دون sudo أو روابط دخول عامة.
- تعرض الطلبات التي لديها سجلات تحضير native؛ السيارة أو الطاولة والأصناف وملاحظات الزبون. تظهر أقدم 100 طلب غير ملغى وغير مسلّم، مع تنبيه إذا زادت النتائج.
- حالات مستقلة: جديد ← قيد التحضير ← جاهز ← تم التسليم. لا تعديل للدفع أو المخزون أو القيود المحاسبية. إعادة الضغط لنفس الحالة آمنة، والقفز أو الرجوع من شاشة قديمة مرفوض. POST مع CSRF وقفل السجل وصلاحيات الكتابة.
- تحديث كامل للوحة كل 10 ثوانٍ؛ هذه آلية أولية وليست بثاً لحظياً أو دعماً للعمل دون اتصال.
- نصوص QWeb قابلة للترجمة بنظام Odoo وترجمة عربية أولية؛ بقية اللغات غير مترجمة بعد. تصميم أولي لا يمثل اعتماد الهوية النهائية.

## أدلة محلية مؤكدة

على قاعدة سيف التجريبية `pos_demo20`، أُنشئ عبر واجهة الزبون طلب سيارة موسوم `TEST-1610` برقم `260-1-000013`، شاي كرك واحد، 0.400 ر.ع.، وملاحظة اختبار واضحة. ظهر الطلب في قائمة POS دون إعادة تحميلها يدوياً، ثم فُتحت أصنافه. ظهر أيضاً في لوحة المطبخ وانتقل من جديد إلى قيد التحضير إلى جاهز من الأزرار. بقي draft وغير مدفوع؛ لم ننفذ دفعاً أو تسليماً أو طباعة فعلية.

اختبار shell نجح لحقول وعلاقات POS. واختبار المطبخ نجح للصلاحيات وتتابع الحالات وتكرار الضغط ورفض القفز وثبات المبالغ؛ تغييرات اختبار shell تُلغى بـ rollback. صورة `evidence/kitchen-ready.png` من شاشة الاختبار. الطلب التجريبي باقٍ جاهز للمراجعة، ولا تُحذف الطلبات السابقة.

## تشغيل الفريق

الجديد: bootstrap يثبت `saif_cafe_kitchen` أيضاً. لبيئة موجودة، ثبّت الإضافة عبر أوامر تشغيل أودو المعتادة مع نفس إعدادات قاعدة التجربة، ثم أعد تشغيل خدمة التطبيق. لا تُعد bootstrap فوق بيانات فعلية ولا تنسخ أسرار سيف. رابط اللوحة يعتمد رقم إعداد الكاشير لديك، وليس بالضرورة 1.

اختبارات regression في `pilot_tests/check_pos_order_loading.py` و`check_kitchen_shell.py` تُشغّل داخل Odoo shell. اختبار المطبخ يحتاج الطلب الاصطناعي الموسوم TEST-1610؛ لا تستبدله بطلب زبون حقيقي.

## حدود متبقية

- لم تختبر Windows أو أجهزة iPad الفعلية أو طابعات الإيصال والمطبخ.
- شاشة المطبخ لا تقسّم الطعام والبار لمحطات منفصلة بعد، ولا ترسل إشعار جاهزية حياً للزبون أو تدمج شارة جاهز في الكاشير.
- تعامل الإلغاء والمرتجع وتعديلات الأصناف بعد بدء التحضير يحتاج اختباراً وتصميماً أوسع؛ اللوحة لا تدّعي إدارة نسخ التذاكر أو الفروق تلقائياً.
- قائمة الطلب تعرض بيانات الطلب الحالية. لا تعتمدها ميدانياً قبل اختبار مسار التعديل والإلغاء مع الفريق.
- واجهة الزبون ما زالت تقول إن متابعة التحضير الحية غير مفعلة؛ هذا صحيح.
- الدفع والإيصال والضرائب واعتماد الأسعار والتصميم واللغات الكاملة ما زالت غير مكتملة.

## إصلاح تشغيل جهاز سيف فقط

Docker كان متوقفاً، وعند تشغيله فشلت نسخة المصدر القديمة بخطأ I/O. حُفظ dump محلي قبل الإصلاح. رُبط تطبيق سيف بمصدر المستودع المشترك السليم عند نفس commit المثبت باستخدام override محلي، وحُدّث start-dev.sh ليستخدمه. لم تُرفع إعدادات الجهاز أو النسخ الاحتياطية أو قاعدة البيانات إلى GitHub. يجب إبقاء مجلد vendor/odoo هذا متاحاً حتى نقل التشغيل إلى ترتيب مستقل.
